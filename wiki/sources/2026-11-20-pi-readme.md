# Pi README（earendil-works/pi 仓库首页）

> 资料性质：GitHub 仓库首页导出的纯文本（README + 页面元数据），导出日期 2026-11-20。README 侧重安装、包结构、安全立场和供应链，**不讲 agent loop 的实现**；扩展、skills、RPC、SDK 等细节都在它链接的 `packages/coding-agent/docs/` 下，不在本资料中。`published` 资料中找不到明确日期，留空。

## 一段话概括

[[pi|Pi]] 自称"一个最小、可扩展、可以变成你自己的 [[agent-harness|agent harness]]"（"a minimal, extensible agent harness that you can make your own"）。它的核心取向是**故意少做**：自带"强力的默认值"，但明确不内置 sub-agents 和 plan mode，也明确没有内置权限系统；缺的能力让用户"叫 Pi 自己造出来"，或安装别人做好的 Pi package。仓库是一个 TypeScript monorepo，从底到顶分为统一 LLM API、agent 运行时、TUI 库和编码 agent CLI 等独立包。

## 解决什么问题

- 主张："Adapt Pi to your workflows, not the other way around."——反对 harness 把工作流写死。Pi 把"哪些能力该内置"的决定权交还用户。
- 提供四种使用形态，覆盖从人用到被程序集成：交互式 TUI、print / JSON 模式（自动化）、RPC（被其他进程控制）、Pi TypeScript SDK（嵌入应用）。README 举 OpenClaw 作为真实集成案例。
- 附带目标：收集真实的开源编码会话数据。作者呼吁用户公开分享会话，理由是真实任务、工具使用、失败和修复比"toy benchmarks"更能改进编码 agent（作者主张）。

## 架构与关键设计决策

### 包划分（README "Packages" 表）

| 包 | 职责（README 原文意） |
|---|---|
| `@earendil-works/pi-ai` | 统一的多 provider LLM API（OpenAI、Anthropic、Google 等） |
| `@earendil-works/pi-agent-core` | agent 运行时：tool calling 与状态管理（[[agent-loop\|agent loop]] 所在层） |
| `@earendil-works/pi-coding-agent` | 交互式编码 agent CLI（`pi` 命令） |
| `@earendil-works/pi-tui` | 终端 UI 库，differential rendering（差量渲染） |
| `@earendil-works/pi-durable` | durable（持久化）的 conversation、task、document 运行时 |
| `@earendil-works/pi-telemetry` | 厂商中立的遥测契约、参考适配器、一致性测试、类型化 schema |
| `@earendil-works/chord` | 跨进程应用的对象运行时：contracts、documents、store、links、带热重载的 plugins、HTTP、workers、web 与终端客户端 |

分层含义（我的归纳）：`pi-ai` → `pi-agent-core` → `pi-coding-agent` 是 LLM 抽象、loop、产品三层，各层可单独被外部项目依赖（README 专门有一节讲如何在 monorepo 之外消费本地构建的 `pi-agent-core`、`pi-durable`）。`pi-durable` 与 `pi-telemetry` 分别对应 [[session-log|会话持久化]]/[[long-running-agents|长时间运行]] 和 [[verification-and-observability|可观测性]]，但 README 只有一句话描述，机制未知。Slack/聊天自动化和 workflow 被拆到独立仓库 `earendil-works/pi-chat`。

### 关键决策一：最小核心，能力外置

- 四种定制手段：extensions、[[skills]]、prompt templates、themes；它们可以打包成 **Pi package**，通过 npm 或 git 分享（见 [[plugins-and-extensibility]]）。
- 明文不内置的功能："Pi ships with powerful defaults but skips features like sub-agents and plan mode. Ask Pi to build what you want, or install a package that does it your way."——[[subagents|subagent]] 和 plan mode 被视为"应由用户或社区按自己的方式实现"的东西，而不是 harness 的必备件。
- 作者给出的理由就是开头那句"让 Pi 适应你的工作流"；README 没有进一步论证（例如为什么 subagent 不适合内置）。

### 关键决策二：不做权限系统，隔离交给容器

README 原文立场非常明确：Pi **没有**内置的[[permissions|权限系统]]来限制文件系统、进程、网络或凭据访问，默认以启动它的用户和进程的权限运行。需要更强边界时"把 Pi 容器化或放进沙箱"，并给出三种模式：

1. **Gondolin extension**：`pi` 进程和 provider 凭据留在宿主机，内置工具和 `!` 命令被路由进本地 Linux micro-VM。
2. **Plain Docker**：整个 `pi` 进程跑在本地容器里，做简单隔离。
3. **OpenShell**：整个 `pi` 进程跑在受策略控制的沙箱里。

第 1 种把"模型凭据"和"工具执行环境"分在边界两侧，第 2、3 种是整体隔离——这是一个值得记下的设计维度。README 没有解释为何不做应用层权限确认；合理的**推断**是作者认为应用层的逐次确认既打断流程又不是真正的安全边界，但这需要其他资料佐证。

### 关键决策三：把供应链当作 harness 的一部分

"We treat npm dependency changes as reviewed code changes." 具体做法：

- 直接外部依赖锁定精确版本；`.npmrc` 设 `save-exact=true` 和 `min-release-age=2`（解析时避开当天发布的依赖版本）。
- `package-lock.json` 是依赖的唯一事实来源，pre-commit 默认拦截 lockfile 变更，除非显式设 `PI_ALLOW_LOCKFILE_CHANGE=1`。
- 官方安装器（pi.dev）按由根 lockfile 生成的 install-lock 安装，连传递依赖也锁定；直接 `npm install -g` 则**不**锁传递依赖。
- 安装、更新、CI 一律 `--ignore-scripts`；带 lifecycle script 的新依赖需要进入显式 allowlist 才能通过检查。
- 定时 workflow 跑 `npm audit` 和 `npm audit signatures`；发布的 tarball 与本地冒烟测试用的是同一份，不重新打包。
- Release 附带带 `SHA256SUMS` 的源码归档，可离线复现官方二进制的构建。

对一个默认拥有用户全部权限、又会执行 shell 的 agent 来说，这等于把防线从"运行时权限"挪到了"安装了什么代码"和"在哪里运行"上（这句是我的归纳）。

### 其他

- 模型目录：构建时从 pi.dev 的 model catalog 取数据，运行时再叠加更新的目录；Nix 构建是离线的，使用 pin 住的目录版本。
- 认证：在 Pi 里运行 `/login` 连接订阅或 API key。
- 运行环境：Node.js 22.19 及以上；支持 macOS、Linux、Windows；提供 Nix flake（ARM64 与 x86-64 的 Linux/macOS）。
- [[context-files|上下文文件]]：仓库根有 `AGENTS.md`，README 说它是"项目专属规则（对人和 agent 都适用）"。长期规划写成 RFC（rfc.earendil.com）。

## 适用与不适用场景

适用：

- 想要一个小而可改的底座，自己决定工作流、愿意写或安装扩展的开发者。
- 需要把 agent 嵌入自己产品的团队（RPC、SDK、可单独依赖的 `pi-agent-core`）。
- 已经有容器或沙箱基础设施、不想要应用层确认弹窗的人。

不适用：

- 期望开箱即有权限确认、plan mode、subagent 的用户——README 明说这些不在内置范围。
- 不能提供外部隔离、又要在敏感环境直接运行的场景：默认即启动者的全部权限。
- 想给仓库提 issue/PR 的新贡献者要注意：新贡献者的 issue 和 PR 默认被自动关闭，维护者每天复查被自动关闭的 issue。
