# Harness engineering：在智能体优先的世界中利用 Codex（OpenAI）

## 一段话概括

[[openai|OpenAI]] 工程师 Ryan Lopopolo 2026-02-11 的实践报告：一个小团队用五个月构建并交付了一款内部 beta 产品，约一百万行代码**没有一行由人手写**，全部由 [[codex|Codex]] 生成。文章的主题是：当工程师不再写代码，工作就变成"设计环境、明确意图、构建反馈回路"——也就是 [[harness-engineering|harness engineering]]。具体经验集中在五点：把仓库做成 agent 的唯一知识来源；AGENTS.md 只当目录而不是百科；用 linter 和结构测试机械地强制架构不变量；让应用的 UI、日志、指标对 agent 可读以便自我验证；用后台 agent 持续"垃圾回收"来对抗熵增。口号是"人类掌舵，智能体执行"。

> 说明：raw 文件是简体中文官方译文，标题把 "Harness engineering" 译成了"工程技术"；正文从未直接出现 harness 一词，只在结尾说"纪律更多体现在支撑结构上，而不是代码上"。本页术语按英文 URL slug 还原，属笔者推断。

## 要点

### 工程师角色的转变

- 团队自设硬约束：**不手动写代码**。目的是逼自己去构建能把工程速度提升数量级所需的东西。
- 早期进展比预期慢，作者归因于**环境规范不足**而非 Codex 能力不足：agent 缺少完成高层目标所需的工具、抽象和内部结构。
- 工作方式是深度优先：把大目标拆成小的构建模块（设计、代码、评审、测试等），让 agent 先把这些模块做出来，再用它们解锁更复杂的任务。出问题时答案几乎从不是"再努力一点"，而是问："缺什么能力？怎样让这个能力对 agent 既**清晰可读**又**可强制执行**？"
- 人几乎只通过 prompt 交互：描述任务 → 运行 agent → 让它开 PR。Codex 被要求在本地自审、请求本地和云端的其他 agent 审查、回应人和 agent 的反馈，循环到所有 agent reviewer 满意（作者称之为 Ralph Wiggum 循环）。人可以 review PR 但不是必须；审核工作已几乎全部变成 agent 对 agent。

### 让应用对 agent 可读（应用层的可观测性）

- 瓶颈从写代码转移到**人工 QA 能力**，所以要让 UI、日志、指标直接对 Codex 可读——这是 [[verification-and-observability|验证与可观测性]] 在 harness 外部环境上的落地。
- 应用可以按 git worktree 启动，每次改动都有一个独立实例可供 Codex 启动和驱动。
- 把 Chrome DevTools Protocol 接入 agent 运行时，并写了处理 DOM 快照、截图、导航的 [[skills|skills]]，让 Codex 能复现 bug、验证修复、直接推理 UI 行为。
- 每个 worktree 配一套**临时的**本地可观测性栈（日志、指标、trace），任务结束即销毁；agent 用 LogQL 查日志、PromQL 查指标。作者称，有了这些，"确保服务启动在 800ms 内完成""四个关键用户旅程中任何 span 不得超过两秒"这类 prompt 才变得可执行。

### 仓库即记录系统：AGENTS.md 是地图不是手册

- 作者把 [[context-management|上下文管理]] 列为让 agent 胜任大型复杂任务的最大挑战之一。早期教训："给 Codex 一张地图，而不是一本 1000 页的说明书。"
- "一个巨大的 AGENTS.md" 方案失败，作者给出四条理由：
  1. **上下文是稀缺资源**：巨大的指令文件挤掉任务、代码和相关文档，agent 要么漏掉关键约束，要么去优化错误的约束。
  2. **过多指导等于没有指导**：一切都"重要"时，agent 只会做局部模式匹配。
  3. **立刻腐烂**：变成陈旧规则的坟场，agent 无法判断哪些还有效。
  4. **难以验证**：单个大文件无法做覆盖率、新鲜度、归属、交叉链接等机械检查，漂移不可避免。
- 最终做法：AGENTS.md 约 100 行，注入上下文，只作目录，指向结构化的 `docs/` 目录（design-docs、exec-plans、generated、product-specs、references，以及 DESIGN/FRONTEND/PLANS/QUALITY_SCORE/RELIABILITY/SECURITY 等顶层文档）和 ARCHITECTURE.md。这是 [[context-files|context files]] 的一种具体组织方式，作者称为**渐进式披露**（progressive disclosure）：从一个小而稳定的入口开始，被告知下一步去哪看。
- **计划是一等工件**：小改动用临时轻量计划；复杂工作写 execution plan，附进度和决策日志并提交进仓库。活跃计划、已完成计划、技术债清单都版本化并集中存放。
- **机械保鲜**：专门的 linter 和 CI 作业检查知识库是否更新、是否交叉链接、结构是否正确；一个定期运行的 "doc-gardening" agent 扫描与真实代码行为不符的过时文档并开修复 PR。

### Agent legibility（对 agent 的可读性）

- 原则：从 agent 角度看，运行时上下文里访问不到的东西等于不存在。Google Docs、聊天记录、人脑里的知识都不可见；只有仓库内版本化的工件（代码、Markdown、schema、可执行计划）可见。Slack 上达成的架构共识如果没进仓库，agent 就像晚入职三个月的新人一样不知道。
- 由此带来的技术选型倾向：偏好能在仓库内被完全理解的依赖和抽象；"无聊"的技术因可组合性、API 稳定和在训练数据中的充分覆盖而更容易被模型建模；有时让 agent 重新实现一个功能子集，比绕开公共库里不透明的上游行为更便宜（例：自己实现带并发限制的 map 辅助函数而不引入 p-limit 风格的包，与 OpenTelemetry 埋点集成，测试覆盖率 100%）。

### 强制不变量，而不是微观管理实现

- 单靠文档无法让全 agent 生成的代码库保持连贯。做法是**强制不变量**：例如要求在边界处解析数据形状（parse, don't validate），但不规定用哪个库。
- 严格的分层架构：每个业务域内代码只能沿固定层次"向前"依赖（Types → Config → Repo → Service → Runtime → UI）；认证、连接器、遥测、feature flag 等横切关注点只能通过单一显式接口 Providers 进入。由自定义 linter（也是 Codex 写的）和结构测试机械执行。
- "品味不变量"：结构化日志、schema 和类型的命名约定、文件大小上限、平台相关的可靠性要求，都用自定义 lint 静态强制。**lint 的错误信息里直接写入修复指引**，等于在出错时把指令注入 agent 上下文。
- 作者的判断：这种架构通常要到几百名工程师时才会引入，但对 coding agent 是早期前提——有了约束，速度才不会下降，架构才不会漂移。边界集中强制，边界之内给 agent 很大自由；生成的代码不必符合人的风格偏好，只要正确、可维护、对未来的 agent 运行可读。
- 人的品味回流路径：review 评论、重构 PR、用户侧 bug → 文档更新，或直接编码进工具；"文档不够时，把规则变成代码"。

### 合并理念、自主程度、熵

- **减少阻塞性合并门**：PR 生命周期短；flaky test 通常靠后续重跑解决而不是无限期阻塞。理由是在 agent 吞吐远超人类注意力的系统里，"纠错成本低，等待成本高"。作者明说在低吞吐环境里这样做是不负责任的。
- **端到端自主**：仓库最近跨过的门槛是，给一个 prompt，Codex 可以验证代码库现状 → 复现 bug → 录故障视频 → 实现修复 → 驱动应用验证 → 录修复视频 → 开 PR → 回应反馈 → 检测并修复构建失败 → 仅在需要判断时升级给人 → 合并。作者强调这**高度依赖该仓库的特定结构和工具**，不应假定可泛化。
- **熵与垃圾回收**：Codex 会复制仓库里已有的模式，包括不好的，时间一长必然漂移。最初靠人每周五（一周的 20%）清理 "AI 残渣"，不可扩展。改为把"黄金原则"编码进仓库，并定期运行后台 Codex 任务扫描偏差、更新质量评分、发起定向重构 PR。举例的两条原则：优先用共享工具包而非手写辅助函数；不做 "YOLO 式"数据探测，要么在边界验证，要么依赖类型化 SDK。

## 值得记下的数据和论据

以下均为 OpenAI 团队**自述**，无第三方验证，产品未公开：

- 时间线：2025 年 8 月下旬首次提交到空仓库；初始脚手架由 Codex CLI + GPT-5 在少量现有模板指导下生成，连最初的 AGENTS.md 也是 Codex 写的；文章发表于 2026-02-11（约五个月后）。
- 规模：约 **100 万行**代码（含应用逻辑、基础设施、工具、文档、内部开发者工具）；约 **1,500 个 PR** 被打开并合并。
- 团队与吞吐：起初 **3 名**工程师，平均每人每天 **3.5 个 PR**；团队扩到 **7 人**后作者称吞吐量还增加了（未给数字，也未说明是人均还是总量）。
- 效率：估计只用了手写所需时间的约 **1/10**——是估计值，没有说明估算方法或对照。
- 使用：数百名内部用户，含每日使用的重度用户，另有外部 alpha 测试者。
- 单次 Codex 运行经常在一个任务上持续工作**超过 6 小时**（常在人睡觉时），是 [[long-running-agents|长时运行 agent]] 的一个实例数据点。
- AGENTS.md 约 **100 行**。
- 清理成本：改造前每周 **20%** 的人力（周五）用于清理；改造后大多数自动重构 PR 可在**一分钟内** review 完并自动合并。

## 作者主张与有证据支撑的结论

- **有一手实践支撑（单一团队、单一仓库）**：大 AGENTS.md 方案失败及其四种失效方式；人工周五清理不可扩展；可观测性栈和 CDP 接入后 agent 能自行复现和验证；端到端自主流程在该仓库可行。
- **作者主张 / 判断**：1/10 时间的估计；"无聊技术对 agent 更友好"；严格分层架构是 coding agent 的早期前提；少设合并门在高吞吐下"通常是正确选择"；技术债应像垃圾回收一样小额持续偿还。这些都没有对照实验。
- **作者自己划的边界**：端到端自主行为不应在没有类似投入的情况下假定可泛化；全 agent 生成的系统中架构连贯性如何随年头演变、人的判断在哪里杠杆最大、模型变强后这套系统如何演变，均"尚不清楚"。

## 与同批资料的关系

- **印证**：Anthropic 的长时运行 harness 文章同样靠仓库内工件（进度文件、feature list、git 历史）传递跨 session 状态，同样给 agent 接浏览器自动化做端到端验证。
- **补充 / 扩大范围**：Anthropic《Building effective agents》把 ACI 限定在工具定义层；本文把"为 agent 设计接口"扩大到整个仓库、文档体系、lint 错误信息和可观测性栈。也因此本文的 "harness" 含义比 Microsoft 文档定义的"运行时脚手架"宽得多——后者是 [[agent-harness|agent harness]]（驱动模型和工具调用的那层程序），本文谈的是 harness 之外、由团队搭建的仓库级环境。两种用法需要在概念页里分开。
- **潜在分歧**：本文主张少设阻塞性合并门、flaky 重跑；Anthropic 长时运行文章要求每个 session 留下可合并的干净状态、测试通过才标完成。前者以"多 agent 高吞吐 + 持续垃圾回收"兜底，后者是单 agent 串行场景。
